# 转写预计时间与后台处理：功能设计及实施计划

**目标：** 提交成功后展示预计剩余时间；用户离开页面、切后台或关闭小程序，服务器继续处理，再次进入读取最新结果。

**架构：** 沿用服务器 SQLite 持久队列和单 worker，不依赖小程序后台计时或常驻。新增服务端只读预计耗时模块，为提交、列表、详情返回一致估算；客户端只负责展示与前台轮询。不改变转写模型、历史正文和每日额度。

**技术：** Python/FastAPI/SQLite；微信原生小程序 JavaScript/WXML；pytest 与 Node 测试、微信开发者工具验收。

## 用户流程与界面

1. 提交确认窗说明“提交成功后，可切后台或关闭小程序，稍后在我的文字查看”。只有服务器接收成功才视为已提交；提交网络失败提示回记录页核对，避免重复提交。
2. 任务列表与详情显示真实阶段：排队、下载音频、转写、完成、失败。活跃任务显示“预计还需约 X—Y 分钟”，短任务显示“不足 1 分钟”；排队显示前方任务数和包含等待的范围。
3. 时长未知、前方任务时长未知，显示“正在估算”；没有历史样本时使用保守初始模型并标明估算。不会显示虚构百分比或精确完成时刻。
4. 实际超过估算上限时显示“处理时间超出预估，仍在继续”，不显示 0 秒或误报完成。失败状态只显示错误及现有处理入口，不继续估算。
5. 详情提供“返回我的文字”按钮，并说明手机无需保持亮屏。列表仅有活跃任务时显示后台说明。
6. 前台每 5 秒读取真实状态；页面隐藏或卸载即停止轮询，服务器不取消任务。回到页面立即刷新；旧请求返回不能覆盖新请求或重新开启隐藏页轮询。请求失败时保留已有记录，明确网络异常不取消已提交任务并允许重试。
7. 不新增订阅消息、推送、手机系统后台服务；本轮的“后台处理”指服务器持续执行，完成后返回查看。服务器断电/停机仍会影响任务，现有重启中断任务明确失败，不承诺断点续转。保留期沿用 7 天。

## 估算规则及接口

- 新增 backend/mini/estimates.py；一次快照读取活跃队列、节目时长和最近最多 30 条同模式成功任务计时，不读取其他用户正文或返回身份。
- 初始处理预算采用 30 秒固定启动开销 + 音频时长的 0.25 倍，范围为预算的 0.6—1.8 倍，最少 15—30 秒。历史样本满足有效时长后，用转写时间/音频时间比率中位数校准，限制在合理范围，保留启动开销，使用宽范围避免短样本虚假精度。
- 下载/转写阶段优先使用探测音频时长，扣除本阶段已用时间；排队任务累加前方全部活跃任务预计剩余时间。未知前序任务时不伪造完整等待估算。队列按 created、id 稳定排序。
- JSON 增加 estimate：remaining_lower_seconds、remaining_upper_seconds（未知为 null）、queue_ahead、overdue、basis（initial/history/unknown）。仅活跃任务返回估算，终态为 null。所有数值取服务器当前时间计算；不存储额外个人数据，不修改数据库表结构。
- app.py 在完成鉴权后，统一给提交/列表/详情附加 estimate；旧客户端可忽略新字段，新客户端兼容旧服务没有 estimate 的情况。

## 验收与回滚

服务端估算测试及原有回归通过；客户端展示/生命周期测试通过；真实提交后退出页面不取消任务，重进可读取同一 ID。不得为了验证而删除用户数据或中断活跃转写。

部署前备份受影响代码，失败时还原代码并重启同一任务；数据库无迁移。保留真实任务和备份。完成后报告实测耗时与估算范围，不将单集样本视为所有音频准确率保证。
